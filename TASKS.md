`@fxtoolkit/indicator-runner`. Roadmap and rationale: the approved plan
(`fxtoolkit-indicators-plan.md`).

**Finding — how asc resolves a package import:** `asc` does **not** read `ascMain`, and it does not walk
`node_modules` up from the importing file. For a bare specifier it tries `<base>/<pkg>/<subpath>.ts` then
`<base>/<pkg>/<subpath>/index.ts`. Orion only worked because its entry was literally
`packages/orion-indicator-stdlib/index.ts`. Fix: the stdlib entry sits at the package root as `index.ts`, and the
build passes `--path <repo>/node_modules` (the dir containing the `@fxtoolkit/indicator-stdlib` symlink).

**Note — bytes are not identical (and can't be):** our binaries match the golden binaries in *size, imports,
exports, and descriptor*, but not byte-for-byte. `asc` is deterministic (verified by repeat compile) and our sources
are byte-identical to Orion's except the header comment and the package rename, so the delta is asc's internal
interning order following the stdlib's new module identity (`~lib/@fxtoolkit/indicator-stdlib/index.ts` vs Orion's
root-level `~lib/orion-indicator-stdlib.ts`). Byte-parity is unachievable once the package is renamed; it was never a
requirement. Behavioral parity is proven in M3.

**Carry into M10 — the golden binaries are stale:** they are **not** reproducible from Orion's *current* sources with
the installed `asc` (0.28.20) — an Orion-source rebuild differs from the committed golden. Descriptors do match, so
the golden is still a valid reference, but M10's parity harness must compare **behavior**, not bytes.

**Frame contract — pinned by inspection, not guessed.** I grepped the whole indicator render path
(`indicator-scene-adapter.ts` + `scene-command-utils.ts` + `getIndicatorObjectEndScreenPoint`) for
`frame.*` and built *only* what is consumed: `timeToX`, `valueToY`, `visibleTimeRange`,
`timeFrameMs`, `plotWidth`, `plotHeight`, `pixelsPerBar`, `plotRightX`, `plotOffsetX`,
`visiblePriceRange`, `areTimesAdjacent`, `timeOrigin`, plus `dataRevision` (the compositors' cache
key). Orion's other frame fields (`allBars`, `visibleBars`, `series`, `yScales`, `priceToY`,
`timeToLogical`, `data`) are **not** included — nothing in the render path reads them. Add them
when a ported file actually needs one.

**Reimplemented rather than ported (the plan anticipated this):** `viewport.ts` and `frame.ts`.
Orion builds its frame from the chart's `generalStore`, pane/plot managers and document-backed scale
configs. The standalone equivalent derives everything from a bar series, a viewport and a plot box:
`pixelsPerBar = plotWidth / visibleBarCount`, `timeOrigin` = logical position of the first visible
bar, `timeToX = plotOffsetX + pixelsPerBar * (logical(time) - timeOrigin)`. Orion's `Q = 40`
zoom-window constant is therefore not carried over.

**Deviation worth noting:** the logical time scale anchors positions to absolute time divided by the
step (`positions[0] = times[0] / step`), so logical values are *not* bar-relative — only their
differences are. The frame's projections depend only on differences, so this is invisible to the
renderer, but it is a real trap when writing tests (it caught two of mine).

**No bar-store class.** The plan mentioned a "minimal bar store". Nothing needs one yet: the worker
owns bar state for execution, and the renderer only needs an immutable array plus a revision, which
`createChartFrame(options)` and `options.dataRevision` already take. Revisit only if the mounting
layer needs mutation/dirty tracking.

**On the parity gate — why no shared-geometry refactor.** The obvious move was to extract one geometry
builder both backends call, making parity structural. I deliberately did **not**: the two backends then
could not diverge, and the test would assert a tautology. Instead each backend builds geometry as Orion
does, and both expose `getLayerGeometry(id)`, so the test compares two independently-computed buffers
and can actually catch divergence. Parity currently holds across four indicators and three zoom levels.

**Finding — `bufferUploads` is not a layer-only metric.** It also counts the per-command sprite vertex
upload, which happens every frame by design. I only established this by instrumenting a temporary test:
layer uploads happen **once** (`bufferData +5`, then `+0` on repeat frames) while `geometryRebuilds`
stays flat and `geometryCacheHits` climbs 0 → 4 → 8. The reuse test now asserts rebuilds/hits counts
rather than raw GL calls, which is unambiguous.

**Whitelisting falls out of the design.** Because `asc` resolves bare specifiers by *asking* `readFile`,
refusing unknown paths in the resolver is the entire security boundary — there is no separate policy
step to keep in sync. `../../../etc/passwd` and `some-other-package` both fail as ordinary not-found
errors, and a test pins each.

**Finding — AssemblyScript's diagnostic category for errors is `3`, not `0`.** My first mapping
assumed `Error = 0` and silently classified every error as `info`, which made three tests fail with the
`ok` flag correct but no error-level diagnostic. Established by dumping a real parse failure's raw
diagnostic rather than guessing again.

**Two build-order couplings, both made explicit rather than papered over:**
1. The embedded stdlib source is generated, so `typecheck` must pack it first (`build:stdlib-source`,
   which the root `typecheck` now runs).
2. `compileScriptIsolated` spawns a worker from its **built** output (`compile-worker.js` is a separate
   emitted entry), so it cannot run from source. The test loads it from `dist`, with the specifier
   assembled at runtime so type-checking does not depend on the build having run.

**Dependency note:** added `@assemblyscript/loader` as a real dependency (needed to read the compiled
descriptor). `assemblyscript` stays an optional peer, so the documented contract is "install it where
you compile".

**Why the consumption model is tarballs, not a git URL.** I tested npm's git support directly: a git
URL to this repo installs the **root** package (`fxtoolkit-indicators`, private, no exports), and the

subdirectory of a git repo. Tarball URLs work because a tarball *is* a package root, and they also ship

**Compared by behaviour, never bytes.** The committed golden binaries are not reproducible from
Orion's current sources with the installed `asc`, so byte equality would be a meaningless gate. What
is compared: resolved params, every step's outputs, `savedState`, and render geometry digests.

**The shared runner is the key design choice.** Rather than reimplementing scenario semantics on each
side (which would let the two drift while still "passing"), one file defines the semantics and both
sides execute it. Orion's vitest importing a file outside its own tree by absolute path works — that
is verified, not assumed, and it is why the tool needs no vendored copy.

**Realtime coverage.** The `__realtime` scenarios feed a provisional live bar and its commit, replaying
committed state via `restore(snapshot)` before each `processBar` — the same sequence Orion's worker
uses for a live bar. That exercises `saveState`/`loadState` round-tripping, not just the history path.

`expected-history` oracle the committed fixtures total ~7 MB. The `__default-history` scenarios are
redundant with the M1 oracle and could be dropped if that becomes unwelcome.

**Status: this is the gate.** Everything it covers passes. The swap itself (deleting Orion's indicator
runtime and renderer, and pointing Orion at these packages) is deliberately **not** done here — it is
your call, and it is the next piece of work rather than part of this port.

## Post-M10 — two defects found while writing the usage guide

Both surfaced from documenting real usage rather than from a test. Both silently produced wrong
output instead of failing loudly.

### 1. Indicator output fell outside the price domain

`mountIndicatorSurface` built its price domain from bar highs/lows only, so an indicator plotting
outside the bar range was drawn off-screen and clipped — silently wrong, no error.

- `IndicatorRenderer.getVisiblePriceExtents(frame?)` now accepts a frame: a caller building a frame
  needs the extents to feed back into that same frame, before anything has rendered.
- The surface builds a **provisional frame**, asks the renderer for extents, then builds the final
  frame with `additionalPriceValues`. There is no circularity — extents depend only on the viewport
  (visible time range and plot size), never on the price domain, and the adapter's extents cache is
  keyed on the viewport, so the second pass reuses it rather than recomputing.
- Extents are for the **primary scale only** (`getVisiblePriceExtents` already filtered to `"price"`),
  so a series on its own `scaleId` cannot distort the main domain.

### 2. In-place bundle mutation served stale geometry

`setBundles` marked a layer dirty only when the bundle *object identity* changed. The documented
realtime pattern — `applyIndicatorBundleDelta(bundle, delta)` mutating in place, then handing the same
array back — is invisible to that check, so the surface kept rendering stale geometry.

- Both renderers now **always invalidate** in `setBundles`. Calling it already means "the indicator
  output changed"; the identity check was a premature optimisation with a silent-failure mode.
- Frame-to-frame caching is unaffected: `render()` does not call `setBundles`, and the M6 reuse test
  (rebuilds flat, cache hits climbing) still passes.

Both are pinned by tests in `test/mount-surface.dom.test.ts`; each fails against the previous
behaviour.
